# Personal wardrobe and private photos

Priorities 2 and 3 add `/wardrobe/`, linked from Account and the existing My closet section. The public demo, approved rail and mannequin images remain separate. A signed-in account gets its own clothing list; there is no automatic copying of demo garments into personal ownership.

## Activate in Supabase

1. Keep the existing public URL and publishable key in the two GitHub Actions secrets. Email sign-in is already owner-tested. No new frontend secret is needed.
2. Open the intended Supabase project → SQL Editor → New query. Copy the entire [`supabase/setup-personal-wardrobe.sql`](../supabase/setup-personal-wardrobe.sql) and run it. Review first: it creates the base tables, existing import/quota functions, new personal wardrobe RPCs and **private** `wardrobe-private` bucket. It narrows direct wardrobe writes to metadata import and adds authenticated ownership guards. It does not delete existing clothing or activate an AI provider. Existing source migrations remain the canonical components; the setup file assembles them for a fresh or existing project. Re-running this same setup preserves records. Reapply the full setup rather than only the base schema later, so narrowed permissions remain in place.
3. Confirm the query succeeds and `wardrobe-private` is private. Do not make the bucket public. No Edge Function deployment is needed for manual clothing/photo CRUD.
4. After the Pages code deployment, sign in and open Personal wardrobe. If tables/functions are missing, the page shows setup guidance rather than fake success or demo fallback.
5. Add a disposable test garment, upload a test photo, edit it, refresh and sign in on a second device. Verify the same details/photo. Use a second account to verify the first account's records and paths are denied, including signed-URL creation. Test replacement, removal and item deletion. Confirm no object/record remains after completed deletion. Do not use the isolated SQL test harness on a real project.

## Behaviour

- Twenty records per page; local search clearly searches that page. Clothing details include flexible category/type/cultural name, brand, size, fit, colour, material, notes, availability and suitable occasions. Unknown suitability is not inferred. Existing imported descriptions can be edited and given individual photos.
- Each write verifies the current user, binds all requests to that exact token, and relies on database/Storage ownership enforcement. Another account cannot access records through a client-supplied owner field or object path. Sign-out/account changes unmount private state and abort outstanding requests. Already-committed server writes remain scoped to the original user.
- Data refreshes on entry, focus/visibility return, reconnect and every 45 seconds while visible. This is cloud-backed periodic sync, not realtime/offline sync. No private garment/photo data is cached in localStorage. The existing auth SDK still stores the session. Unsaved drafts live in memory and do not survive navigation. Concurrent edits use a revision check and retain the unsaved draft on conflict; load the latest details before retrying. An ambiguous create response requires reload/reconciliation, not a new automatic duplicate insert.
- JPEG/PNG/WebP sources up to 12 MB and 40 megapixels are re-encoded as JPEG (maximum 1600px edge), stripping metadata before upload. Existing preparation rejects oversized/corrupt inputs and prepared payloads above its bound. Bucket upload limit is 3 MB, JPEG only. HEIC conversion is required. Mobile capture is a browser file-picker hint, not a native app or a guarantee of physical camera behaviour.
- One current photo per garment. Original source files are not retained; the resized copy is the cloud photo. The full-outfit import and Rush Hour source photos remain session-only; this new view uploads a separately selected photo explicitly, and does not silently persist those sources.
- Photo object names are immutable random IDs under the authenticated owner and garment. A database reservation precedes upload. Attaching the new photo atomically registers the old one for cleanup. Failed/ambiguous operations retain tracked staged/removing rows. Clean up pending photos discards unfinished uploads/old replacements while keeping the current photo. At most five tracked photos per garment; cleanup is required before adding more.
- Signed previews expire after 60 seconds and are refreshed in memory. Anyone possessing an issued signed URL can use it until expiry or object deletion; sign-out clears the UI but cannot revoke an already-issued link. Private bucket RLS governs issuing URLs and direct reads. Browser/CDN-delivered copies cannot be remotely erased.
- Explicit deletion marks the item unavailable first, then removes tracked objects through the Storage API, confirms their absence, and only then deletes photo/garment metadata. Failed cleanup stays visible as Deletion pending with Retry deletion. Reservations and Storage-policy locks serialize upload metadata against cleanup. Storage physical-blob deletion is performed through the API, never by direct SQL deletion of real `storage.objects` rows. Historical outfit events are retained and can reference a removed garment. Full account deletion/export remains Priority 6.
- The existing personal chatbot reads available confirmed wardrobe records. Deleted/pending-deletion rows are excluded. Existing approved catalogue images are not assigned to personal items by name.

## Tests and limits

- `node scripts/test_personal_wardrobe.cjs`: pinned token, abort/account scope, safe signed URL, missing setup, conflict/offline/foreign-owner and ambiguous-attach contracts.
- CI runs `scripts/test_personal_wardrobe.sql` after existing PostgreSQL RLS/import harnesses in a disposable database. It supplies a minimal Storage schema and tests policy/function enforcement, two users, denied direct lifecycle writes, immutable objects, replacement, incomplete deletion/retry, anonymous rejection and import compatibility. This is not the hosted Storage API or blob engine.
- Isolated configured build (`auth-test.example`, public fake key), then `node scripts/check_personal_wardrobe.cjs`: browser create/edit/photo replacement, reload/second context, retained conflict draft, failed deletion/retry, setup guidance, logout clearing and responsive bounds. All service responses are intercepted fixtures; tests never send user photos or real account credentials.
- Real hosted bucket/API behaviour, physical camera/gallery, cross-device sync and two real accounts still require production acceptance after SQL activation. No live Supabase admin operation is performed by publishing code alone.

## Import the existing closet

Choose **Import my existing closet** in Personal wardrobe. Select your previously catalogued pieces, optionally include their approved catalogue images, confirm ownership, and import. The bundled catalogue currently contains 26 items. Clothing details are inserted into the signed-in user's wardrobe using a stable `catalog:v1:<source-id>` key and PostgreSQL's existing `(user_id, client_item_id)` unique constraint. Retrying uses `ON CONFLICT DO NOTHING`, then reads back that owner's existing row: it does not overwrite names, availability, notes or other edits. Separate accounts can explicitly import their own copies.

Photos are copied from strictly bounded same-origin `/catalog/` image paths into the existing private bucket. They remain illustrative catalogue imagery, not new photography. The importer attaches an image only when the item has no photo and is still at its initial revision. Previously edited items and existing photo choices are kept. The source catalogue is never changed. Source and destination ownership/key checks prevent interpreting an unrelated returned record as the imported item.

Progress is per item, not one global transaction. Stop cancels pending requests/queued work; completed records remain. An ambiguous request may already have committed; repeat the same selection to reconcile without duplicate clothing records. Failed photo attachment remains tracked by the existing private photo lifecycle. Clean up pending photos in Personal wardrobe before retrying that item. A pending-deletion item must finish deletion before reimport. Permanent deletion removes the source key with its record; a later explicit import can create that piece again. No automatic import runs on sign-in, and no service-role key or additional migration is needed beyond the existing personal wardrobe setup.

## Local photo-cleanup preview

Both Upload/Replace photo and Take photo open a review dialog before any upload. Choose **Save cleaned photo** only after checking garment edges, colour and details, or choose **Use original photo** to keep the source appearance with normal bounded upload preparation. Cancel clears the unsaved preview and sends no photo. The approved saved file continues through the existing private upload/replacement and cleanup flow.

- Pixel-based plain-background removal uses colour-distance flood fill connected to image edges. Uneven corner colours skip automatic removal with an explicit warning. Similar foreground/background colours, complex backgrounds, shadows, texture and occlusion can defeat this method. It is not a trained garment segmentation model, person removal or reconstruction of hidden clothing.
- Erase and restore brushes correct the mask using original pixels. Undo removes one brush mark; Reset restores default controls. Crop sliders provide a keyboard-accessible alternative to pointer/touch correction. The original canvas keeps its image aspect ratio so brush coordinates map to source pixels.
- The remaining visible region is centred with margins in a neutral 4:5 frame, up to 1280×1600. Source preprocessing is bounded to a 1600px edge; no new garment detail is generated and retained pixels are not recoloured by default. Optional lighting adjustment changes RGB intensity and may affect perceived colour; default is 0%. Background colour can be neutral, white or dark. The cloud JPEG encoding can introduce ordinary compression/resampling differences.
- Empty masks or invalid crop bounds block cleaned-image saving. Already transparent backgrounds do not treat black garment pixels as a black backdrop. Changing image controls clears the review checkbox; the cleaned save stays blocked until the new preview is reviewed.
- Processing uses local Canvas and typed arrays. No AI model download, third-party processing, paid service or runtime dependency is introduced. Source/previews are in memory only. The saved result replaces the existing current photo; a separate cloud original/version archive is not added. Full-outfit import and Rush Hour photos retain their existing session-only behaviour and do not use this personal-item editor automatically.

`node scripts/test_photo_cleanup.cjs` verifies mask/crop/brush safety, unchanged source pixel buffers, transparent dark garments, and bounded catalogue assets/metadata. The PostgreSQL ownership suite covers duplicate-safe per-account catalogue inserts and preserved metadata. `node scripts/check_closet_integrations.cjs` exercises confirmed import/photo copying, repeat import without duplicates/overwrites, preview approval/cancel, and responsive bounds using intercepted services. Real personal images, exact mask/colour acceptance, physical touch/camera and hosted bulk-import behaviour still need owner verification.
